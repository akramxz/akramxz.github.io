Del cortafuegos heredado al definitivo

Analicé un cortafuegos con errores típicos, lo comprobé desde Kali y lo sustituí por reglas propias para IPv4 e IPv6. También evalué de forma crítica la herramienta de análisis.

Objetivo

Partir de un cortafuegos «heredado» con los errores típicos que se encuentran en servidores reales, demostrar desde fuera que deja expuestos servicios internos y sustituirlo por un conjunto de reglas propio con política DROP, antispoofing, ICMP limitado y registro. Para analizar las reglas uso fwrule, un analizador de iptables y nftables, y compruebo cada uno de sus hallazgos con tráfico real desde Kali.

Escenario

En el servidor del proyecto 02 (10.66.0.10) instalé tres servicios con un script: una web pública con nginx (80), un panel interno de prueba (8080) y un Redis configurado mal a propósito, escuchando en todas las interfaces y sin modo protegido (6379). Encima cargué el cortafuegos heredado: política DROP, pero con una regla duplicada, una regla que acepta toda la red del laboratorio antes de los bloqueos, una contradicción con el puerto 8080, ICMP sin límite y nada para IPv6.

Lo que se veía desde Kali

Los paquetes con origen falsificado 127.0.0.1 no llegaron a ningún servicio, pero no por el cortafuegos: los descartó el filtro de ruta inversa (rp_filter) que activé en el proyecto 02. Es un buen ejemplo de defensa en capas.

Análisis con fwrule

fwrule está escrito en V. Con la versión actual del compilador (0.5.2) no compilaba, y tampoco entendía las cadenas de usuario de iptables, así que le hice un parche pequeño (incluido abajo). Con el cortafuegos heredado detectó bien los problemas importantes:

Con mi cortafuegos final marcó 6 hallazgos críticos. Los comprobé uno a uno y ninguno era real: la herramienta no tiene en cuenta el tipo ICMP, los límites, las negaciones de interfaz ni que LOG deja pasar el paquete. Esta es mi revisión de todos sus hallazgos:

El cortafuegos final

Escribí las reglas a mano, con un comentario que explica cada bloque. Cada servicio se abre solo a quien lo necesita, todo lo demás pasa por una cadena propia que registra con límite y descarta, y por primera vez hay reglas para IPv6. Además corregí Redis para que escuche solo en localhost.

Para aplicarlo sin riesgo de quedarme fuera escribí aplicar.sh: valida la sintaxis, guarda las reglas anteriores y lanza un temporizador. Si en 120 segundos no confirmo desde una conexión nueva, restaura el cortafuegos anterior solo.

Incidencias y soluciones

ICMP

El límite de ping no funcionaba: 20 de 20 respondidos. Los pings seguidos de un mismo origen comparten identificador ICMP y conntrack los marca como ESTABLISHED, así que los aceptaba la regla de conexiones establecidas antes de llegar al límite.

Moví el límite de ping por delante de conntrack. Después: 6 de 20.

Red de seguridad

Mi temporizador restauró el cortafuegos anterior. El temporizador iba ligado a la sesión SSH, que se quedó abierta hasta que se cumplió el plazo sin poder confirmar.

Lo lancé con setsid y sin heredar la salida. La red de seguridad hizo exactamente lo que debía: sin confirmación, vuelta atrás.

Redis

Redis no arrancaba tras cambiar bind. La sintaxis -::1 es de Redis 6.2 y Ubuntu 22.04 trae la 6.0.

bind 127.0.0.1 ::1 y modo protegido activado.

CIS

La auditoría CIS bajó al instalar los servicios. Al crear el usuario de Redis, apt reescribió /etc/passwd- con permisos 644, y nginx cuenta como servidor HTTP instalado.

Volví a dejar las copias en 600 (98,2 %). nginx queda como excepción justificada: este servidor publica la web.

Laboratorio

Compilar V con las dos máquinas encendidas saturó el portátil y el servidor llegó a dar avisos de CPU bloqueada.

Pausé Kali mientras compilaba y la reanudé después.

Lo que he aprendido

  • En iptables el orden lo es todo: una regla amplia al principio anula todas las específicas que vienen detrás, y los contadores de paquetes lo demuestran.
  • Un cortafuegos IPv4 perfecto no sirve si IPv6 queda abierto.
  • Las herramientas de análisis ayudan, pero hay que verificar sus hallazgos. Con reglas sencillas acertó; con extensiones como limit o icmp-type se equivocó en todos los críticos.
  • conntrack cambia cómo se evalúan las reglas: limitar algo que el sistema considera «establecido» exige colocarlo antes.
  • Aplicar un cortafuegos en remoto siempre con vuelta atrás automática.

# =============================================================================
#  akram-firewall.rules · Cortafuegos final de AKRAM-LAB-SRV01
#  Autor: Akram El Mazzoudi Zarrouk · Proyecto 04 · Firewall Rule Engine
#
#  Principios:
#    - Política DROP en las tres cadenas y una regla por servicio, sin duplicados.
#    - Cada servicio se abre solo a quien lo necesita:
#        SSH   22   -> redes de administración (NAT 10.0.2.0/24 y laboratorio 10.66.0.0/24)
#        HTTP  80   -> cualquiera (web pública)
#        Panel 8080 -> solo la red NAT de administración
#        Redis 6379 -> solo localhost (además ahora escucha solo en 127.0.0.1)
#    - Antispoofing: nada que diga venir de 127.0.0.0/8 o de mi propia IP puede
#      entrar por una interfaz externa, y los paquetes INVALID se descartan.
#    - ICMP limitado: ping a 1/s con ráfaga de 5 y solo los tipos de error útiles.
#    - Lo descartado se registra con límite para no llenar el disco.
#    - SSH sin límite fijo: la limitación adaptativa por IP la hace akram-ssh-guard
#      (proyecto 03); un límite fijo aquí cortaba también mi propia administración.
#    - IPv6 tiene su propio fichero (akram-firewall6.rules): sin él, todo IPv6 quedaba abierto.
#  Se carga con: iptables-restore < akram-firewall.rules (persistente en /etc/iptables/rules.v4)
# =============================================================================
*filter
:INPUT DROP [0:0]
:FORWARD DROP [0:0]
:OUTPUT DROP [0:0]
:AKRAM-LOG-DROP - [0:0]

# --- Registro de lo que se descarta (con límite) -----------------------------
-A AKRAM-LOG-DROP -m limit --limit 5/min --limit-burst 10 -j LOG --log-prefix "AKRAM-FW-DROP: " --log-level 4
-A AKRAM-LOG-DROP -j DROP

# --- Entrada: base (conexiones ya aceptadas lo primero, como sugiere fwrule) ----
-A INPUT -i lo -j ACCEPT
# El ping va ANTES de conntrack: los pings seguidos de un mismo origen comparten
# identificador ICMP y conntrack los marca como ESTABLISHED, saltándose el límite.
-A INPUT -p icmp --icmp-type echo-request -m limit --limit 1/s --limit-burst 5 -j ACCEPT
-A INPUT -p icmp --icmp-type echo-request -j AKRAM-LOG-DROP
-A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
-A INPUT -m conntrack --ctstate INVALID -j AKRAM-LOG-DROP
-A INPUT -s 127.0.0.0/8 ! -i lo -j AKRAM-LOG-DROP
-A INPUT -s 10.66.0.10/32 ! -i lo -j AKRAM-LOG-DROP

# --- Entrada: servicios locales (documentados para CIS 3.3.5) -------------------
-A INPUT -i lo -p tcp --dport 53 -j ACCEPT
-A INPUT -i lo -p udp --dport 53 -j ACCEPT
-A INPUT -i lo -p tcp --dport 6379 -j ACCEPT

# --- Entrada: servicios publicados ---------------------------------------------
-A INPUT -p tcp -s 10.0.2.0/24 --dport 22 -m conntrack --ctstate NEW -j ACCEPT
-A INPUT -p tcp -s 10.66.0.0/24 --dport 22 -m conntrack --ctstate NEW -j ACCEPT
-A INPUT -p tcp --dport 80 -m conntrack --ctstate NEW -j ACCEPT
-A INPUT -p tcp -s 10.0.2.0/24 --dport 8080 -m conntrack --ctstate NEW -j ACCEPT

# --- Entrada: mensajes de error ICMP útiles (el ping está arriba) ----------------
-A INPUT -p icmp --icmp-type destination-unreachable -j ACCEPT
-A INPUT -p icmp --icmp-type time-exceeded -j ACCEPT

# --- Entrada: todo lo demás ------------------------------------------------------
-A INPUT -j AKRAM-LOG-DROP

# --- Salida ---------------------------------------------------------------------
-A OUTPUT -o lo -j ACCEPT
-A OUTPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
-A OUTPUT -p udp --dport 53 -m conntrack --ctstate NEW -j ACCEPT
-A OUTPUT -p tcp --dport 53 -m conntrack --ctstate NEW -j ACCEPT
-A OUTPUT -p tcp -m multiport --dports 80,443 -m conntrack --ctstate NEW -j ACCEPT
-A OUTPUT -p udp --dport 123 -m conntrack --ctstate NEW -j ACCEPT
-A OUTPUT -p icmp -j ACCEPT
-A OUTPUT -m limit --limit 5/min -j LOG --log-prefix "AKRAM-FW-DROP-OUT: " --log-level 4
COMMIT
akram-firewall6.rules (IPv6) · ver código
# =============================================================================
#  akram-firewall6.rules · Cortafuegos IPv6 de AKRAM-LAB-SRV01
#  Autor: Akram El Mazzoudi Zarrouk · Proyecto 04
#  En el escaneo del cortafuegos heredado, nginx respondía por IPv6 (link-local)
#  porque ip6tables estaba vacío con política ACCEPT. El servidor no publica nada
#  por IPv6, así que solo se permite lo imprescindible para que IPv6 funcione.
# =============================================================================
*filter
:INPUT DROP [0:0]
:FORWARD DROP [0:0]
:OUTPUT ACCEPT [0:0]
-A INPUT -i lo -j ACCEPT
-A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
-A INPUT -m conntrack --ctstate INVALID -j DROP
# ICMPv6 necesario: errores y descubrimiento de vecinos (sin esto IPv6 deja de funcionar)
-A INPUT -p ipv6-icmp --icmpv6-type destination-unreachable -j ACCEPT
-A INPUT -p ipv6-icmp --icmpv6-type packet-too-big -j ACCEPT
-A INPUT -p ipv6-icmp --icmpv6-type time-exceeded -j ACCEPT
-A INPUT -p ipv6-icmp --icmpv6-type parameter-problem -j ACCEPT
-A INPUT -p ipv6-icmp --icmpv6-type neighbour-solicitation -m hl --hl-eq 255 -j ACCEPT
-A INPUT -p ipv6-icmp --icmpv6-type neighbour-advertisement -m hl --hl-eq 255 -j ACCEPT
-A INPUT -p ipv6-icmp --icmpv6-type router-advertisement -m hl --hl-eq 255 -j ACCEPT
-A INPUT -m limit --limit 5/min -j LOG --log-prefix "AKRAM-FW6-DROP: " --log-level 4
COMMIT
aplicar.sh · ver código
#!/usr/bin/env bash
# Aplica el cortafuegos final con red de seguridad · Akram El Mazzoudi Zarrouk
# Si en 120 s no se confirma (sudo rm /root/fw-pendiente), se restaura el anterior.
# El temporizador va desligado de la sesión (setsid + sin heredar la salida) para
# que la conexión SSH termine y se pueda comprobar el acceso con otra nueva.
set -euo pipefail
D=/home/akram/lab/proyecto04
iptables-save  > /root/fw-anterior.v4
ip6tables-save > /root/fw-anterior.v6
iptables-restore --test  < $D/akram-firewall.rules
ip6tables-restore --test < $D/akram-firewall6.rules
touch /root/fw-pendiente
setsid bash -c 'sleep 120; if [ -f /root/fw-pendiente ]; then iptables-restore < /root/fw-anterior.v4; ip6tables-restore < /root/fw-anterior.v6; logger -t akram-firewall "sin confirmar: restaurado el cortafuegos anterior"; fi' > /dev/null 2>&1 < /dev/null &
iptables-restore  < $D/akram-firewall.rules
ip6tables-restore < $D/akram-firewall6.rules
logger -t akram-firewall "aplicado akram-firewall.rules (pendiente de confirmar)"
# Redis vuelve a escuchar solo en localhost y con modo protegido
sed -i 's/^bind .*/bind 127.0.0.1 ::1/; s/^protected-mode .*/protected-mode yes/' /etc/redis/redis.conf
systemctl restart redis-server
echo "Aplicado. Comprueba el acceso con otra conexión y confirma con: sudo rm /root/fw-pendiente"
