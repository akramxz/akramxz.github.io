Detector de persistencia en Linux

Ensucié mi servidor con nueve mecanismos de persistencia inertes y evalué de forma crítica un detector: qué encuentra, qué se le escapa y en qué se equivoca.

Objetivo

Comprobar si un detector de mecanismos de persistencia encuentra las puertas traseras que un atacante dejaría en un Linux para sobrevivir a un reinicio. Para probarlo de verdad «ensucié» mi servidor con marcadores en los sitios habituales y pasé el detector. Lo importante de este proyecto es doble: ver qué encuentra y, sobre todo, evaluar con sentido crítico qué se le escapa y en qué se equivoca.

Nota de seguridad

Ninguno de mis marcadores hace nada dañino. No hay shells inversas, ni descargas, ni acceso remoto. Cada uno es solo la señal que dejaría un atacante en ese sitio, pero su «carga» se limita a escribir una línea en el log del sistema con logger o a declarar una variable. Todos llevan la etiqueta AKRAM-LAB-TEST y un script los retira al terminar. Trabajo sobre un snapshot, así que puedo volver atrás en segundos.

El detector

sentinel está escrito en Go y revisa más de doce categorías de persistencia (systemd, cron, perfiles de shell, SSH, LD_PRELOAD, módulos del kernel, reglas udev, init.d, autostart XDG, tareas at, motd y PAM), relacionando cada hallazgo con su técnica MITRE ATT&CK. Lo compilé en el servidor y guardé una línea base del sistema limpio (70 hallazgos ya existentes, casi todos ruido legítimo), para después comparar y ver solo lo nuevo.

De los 9, el detector marcó 4. No es un fallo del detector: los que se le escapan (cron, clave SSH, módulo del kernel, udev) tienen scanners heurísticos, que solo alertan de cargas sospechosas (shells inversas, descargas, rutas en /tmp…). Como hice los marcadores a propósito inofensivos, con el binario legítimo logger, no disparan ninguna alerta. Es el comportamiento correcto: así se evitan miles de falsos positivos. El marcador del perfil de shell sí saltó porque le añadí una referencia a /tmp, que es uno de los patrones que el motor sí reconoce.

Esto deja una lección importante: la detección por carga sospechosa se salta la persistencia que parece inofensiva. La detección por cambio (comparar con una línea base) es más difícil de engañar, porque le da igual lo que haga el fichero: si antes no estaba, salta.

Y también falsos positivos

Al mirar los hallazgos de nivel alto del sistema aparecieron tres cosas marcadas como peligrosas que en realidad son legítimas. Un buen analista tiene que saber descartarlas.

pam_permit.so en common-auth/etc/pam.d/common-authEs parte de la configuración estándar de PAM en Ubuntu; no es una puerta trasera.

El caso del .bashrc es curioso: el detector marca como «alias hijacking» el prompt con mi nombre que configuré en el proyecto 02. Técnicamente tiene razón en que alguien ha modificado el perfil; el trabajo del analista es saber que fui yo.

Incidencias y soluciones

ld.so.preload

El marcador de LD_PRELOAD llenaba la consola de errores. Apuntaba a una biblioteca inexistente, así que cada orden intentaba precargarla y fallaba. El error era inofensivo (la biblioteca «se ignora»), pero muy ruidoso.

Compilé una biblioteca vacía que no hace nada y apunté el marcador ahí. Sigue siendo inerte, el detector lo sigue encontrando y la consola queda limpia.

Línea base

El sistema limpio ya daba 70 hallazgos. Casi todos son ruido legítimo (generadores de systemd, servicios de Ubuntu).

Guardé esa línea base y comparé contra ella, así solo miro lo que cambia de verdad.

Cobertura

De 13 scanners registrados, solo 7 produjeron resultados. Los de cron, SSH, kernel y udev no sacaron nada ni siquiera en un sistema con cron normal.

Lo verifiqué leyendo el código: esos scanners solo alertan de patrones sospechosos, no de la mera existencia de una entrada. No es un error, es su diseño, pero conviene saberlo para no confiarse.

Lo que he aprendido

  • Un detector no es un oráculo: tiene falsos negativos (se le escapa lo que parece inofensivo) y falsos positivos (marca cosas legítimas). Hay que leer sus resultados con criterio.
  • La detección por cambio respecto a una línea base limpia es más robusta que la detección por «mala pinta» de la carga, porque no se la puede engañar con un comando inocente.
  • Entender el código de una herramienta te dice qué cubre de verdad, más allá de lo que promete el README.
  • Trabajar siempre sobre snapshots: planté nueve puertas traseras de prueba y volví a un sistema limpio en segundos.

Código

plantar-marcadores.sh · ver código
#!/usr/bin/env bash
# =============================================================================
#  plantar-marcadores.sh · Marcadores de persistencia INERTES para probar el detector
#  Autor: Akram El Mazzoudi Zarrouk · Proyecto 06 · Persistence Scanner
#
#  IMPORTANTE: ninguno de estos marcadores hace nada dañino. No hay shells
#  inversas, ni puertas traseras, ni descargas, ni acceso remoto. Cada uno es
#  solo una señal que un atacante dejaría en ese mismo sitio, pero aquí su
#  "carga" se limita a escribir una línea en el log del sistema (logger) o a
#  dormir. Sirven para comprobar que el detector mira en los sitios correctos.
#  Todos llevan la etiqueta AKRAM-LAB-TEST para poder limpiarlos después.
# =============================================================================
set -euo pipefail
MARCA="AKRAM-LAB-TEST"
log() { logger -t akram-persist-test "marcador inerte: $1"; }

# 1) cron (T1053.003): tarea que solo escribe en el log, no ejecuta nada externo
cat > /etc/cron.d/akram-test <<EOF
# ${MARCA}: marcador inerte, solo registra una línea
*/10 * * * * root /usr/bin/logger -t ${MARCA} "cron inerte en marcha"
EOF

# 2) servicio systemd (T1543.002): una unidad que únicamente duerme
cat > /etc/systemd/system/akram-test-persist.service <<EOF
[Unit]
Description=${MARCA} servicio inerte de prueba
[Service]
Type=oneshot
ExecStart=/bin/sh -c '/usr/bin/logger -t ${MARCA} "servicio inerte"; /bin/sleep 1'
[Install]
WantedBy=multi-user.target
EOF
systemctl daemon-reload
systemctl enable akram-test-persist.service >/dev/null 2>&1

# 3) perfil de shell (T1546.004): referencia INERTE a /tmp para activar el motor de
#    patrones. Es solo una variable de entorno; no ejecuta ni descarga nada.
cat > /etc/profile.d/akram-test.sh <<EOF
# ${MARCA}: referencia inerte a /tmp para activar el motor de patrones
export AKRAM_TEST_DIR=/tmp/akram-test-dir  # solo una variable, no ejecuta nada
EOF

# 4) clave SSH de prueba (T1098.004): clave generada para la ocasión y etiquetada
mkdir -p /root/.ssh && chmod 700 /root/.ssh
GEN=$(ssh-keygen -q -t ed25519 -N '' -C "${MARCA}-clave-inerte" -f /tmp/akram_test_key <<<y 2>/dev/null; cat /tmp/akram_test_key.pub)
echo "$GEN" >> /root/.ssh/authorized_keys
rm -f /tmp/akram_test_key /tmp/akram_test_key.pub

# 5) ld.so.preload (T1574.006): apunta a una biblioteca que no existe/vacía.
#    No se precarga nada real; es solo la señal en el fichero, que es lo que busca el detector.
echo "/opt/${MARCA}/inerte.so" > /etc/ld.so.preload

# 6) modprobe install hook (T1547.006): un módulo inventado cuyo hook solo registra
echo "install akram_test_mod /usr/bin/logger -t ${MARCA} modulo-inerte" > /etc/modprobe.d/akram-test.conf

# 7) rc.local / init (T1037.004): rc.local que solo escribe en el log
cat > /etc/rc.local <<EOF
#!/bin/sh
# ${MARCA}: rc.local inerte
/usr/bin/logger -t ${MARCA} "rc.local inerte"
exit 0
EOF
chmod +x /etc/rc.local

# 8) update-motd.d (T1546): script de login que solo registra
cat > /etc/update-motd.d/99-akram-test <<EOF
#!/bin/sh
# ${MARCA}: motd inerte
/usr/bin/logger -t ${MARCA} "motd inerte"
EOF
chmod +x /etc/update-motd.d/99-akram-test

# 9) regla udev (T1546): RUN+= que solo registra (no se dispara solo)
echo "ACTION==\"add\", SUBSYSTEM==\"usb\", RUN+=\"/usr/bin/logger -t ${MARCA} udev-inerte\"  # ${MARCA}" > /etc/udev/rules.d/99-akram-test.rules

echo "Plantados 9 marcadores inertes etiquetados ${MARCA}."
limpiar-marcadores.sh · ver código
#!/usr/bin/env bash
# limpiar-marcadores.sh · Elimina los marcadores inertes del proyecto 06 · Akram El Mazzoudi Zarrouk
set -u
rm -rf /opt/AKRAM-LAB-TEST
rm -f /etc/cron.d/akram-test /etc/profile.d/akram-test.sh /etc/modprobe.d/akram-test.conf \
      /etc/update-motd.d/99-akram-test /etc/udev/rules.d/99-akram-test.rules /etc/ld.so.preload /etc/rc.local
systemctl disable akram-test-persist.service >/dev/null 2>&1 || true
rm -f /etc/systemd/system/akram-test-persist.service
systemctl daemon-reload
sed -i '/AKRAM-LAB-TEST-clave-inerte/d' /root/.ssh/authorized_keys 2>/dev/null || true
echo "Marcadores inertes eliminados."
